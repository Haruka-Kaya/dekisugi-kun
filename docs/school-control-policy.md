# 学校 control plane の内部契約と認可核

Issue [#2](https://github.com/Haruka-Kaya/dekisugi-kun/issues/2) の最初の実装単位。
学校版の認証・集計・配布が完成したという意味ではない。

`server/lib/school-control-contracts.ts` は、学校テナント、学校・年度付きクラス、
教職員所属、認証済みセッション、操作対象の正確なフィールドを検証する。
氏名、音声、回答、ランキング、端末ID、任意metadataを追加すると拒否する。
IDは学校ドメインで発行する不透明なIDとし、個人版の端末UUIDやLANキーから所属を推論しない。

`server/lib/school-control-policy.ts` は、信頼するサーバー側adapterから現在の認証状態と
所属・対象を読み、テナント、教職員、クラス、有効期限、MFA証跡を照合する。
返すのは内部用の認可判断と検証した操作対象だけで、HTTP経路やデータ操作は追加していない。
既存 `schoolTestingEnabled()` が閉じる production/preview ではadapterを呼ばず拒否する。
ローカル/明示developmentで既存の内部テストフラグが有効な場合のみ合成試験を実行できる。

## 最小の権限表

| 操作 | admin | teacher | support |
|---|---|---|---|
| 担当クラスの概念集計を読む | 可 | 可 | 不可 |
| 同じテナントの別クラスの集計を読む | 可 | 不可 | 不可 |
| 既存クラス・在籍の管理 | 可 | 不可 | 不可 |
| 教職員・契約枠の管理、監査閲覧、削除依頼 | 可 | 不可 | 不可 |
| 未定義の操作 | 不可 | 不可 | 不可 |

すべてに有効なMFA付き教職員セッションとactiveな所属・テナントが必要。
クラス操作ではactiveなクラスの存在とテナント一致も必要。
supportの具体的な支援フローは未定なので権限を与えない。
`request_deletion` は削除依頼の認可区分であり、削除実行の許可や実装ではない。
この初期表の拡張は、用途とテストを伴う明示的な変更で行う。

## 信頼境界と今後の接続条件

`authenticate()` は、選定した学校IdPの署名、issuer/audience、期限、失効、MFA証跡を
検証した後にだけ内部セッションを返すadapterとする。セッションparserが成功しても
本人確認が済んだことにはならない。HTTP body、個人版トークン、LAN管理キーを
このadapterの返り値へそのまま変換してはいけない。

所属・クラス・テナントadapterもリクエスト中のroleやtenantを信用せず、現在の正本を読む。
将来のデータ操作では、返された検証済み対象を使い、同じtransaction内で所属・対象の
失効を再確認して操作と監査を確定する。認可判断の再利用・キャッシュはしない。
このライブラリのallow結果だけでは、集計payloadの個人情報保護を保証しない。

未実装: 実IdPとの接続、永続保存、在籍・ライセンスの状態機械、年度更新・転出・共有端末初期化、
小集団/差分攻撃を防ぐ概念集計、監査記録、削除・保全・復旧、管理画面、HTTP API。
保持日数やプロバイダを仮決めしていない。
AI・保存先の契約、学校の運用条件、実機受入、公開判断は
[`school-readiness.md`](school-readiness.md) の条件を引き続き満たす必要がある。
Issue #2 は未完了のまま維持する。

## 検証

`cd server && npm test`。新規試験は合成IDとメモリ内adapterのみを使う。
tenant/主体/クラス差替え、権限昇格、失効、MFA欠落、adapter障害、未知操作、
余分な個人情報field、非同期処理中の対象変更、production/previewのzero-call拒否を検証する。
外部AI・IdP・実データへの接続は行わない。
